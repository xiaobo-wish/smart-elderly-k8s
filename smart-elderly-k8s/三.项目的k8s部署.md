### 2.为什么要迁移到k8s集群上

首先docker compose 解决的是一台机器上的部署，它将docker run 参数写成文件，可以直接一键拉起多个容器。但是

1.它只能在一台机器上面跑，有单点故障的问题

2.他没有自愈的功能，容器挂了不会自己重新拉起

3.没有弹性伸缩，滚动发布的功能

4.配置/密码散落在文件里，不好统一管理

5.服务发现虽然支持服务名 DNS，但主要局限在 Compose 网络范围内，不能解决集群级服务发现和负载均衡

###### 而k8s不同

他将启动进程变成资源文件中的声明目标状态，交给调度器去完成

1.pod中的容器挂了会自动重启，由Deployment来保证副本数

2.滚动升级，扩缩容一条命令实现

```powershell
直接改镜像触发滚动升级：kubectl set image deployment/my-app app=registry/app:v2 -n xhzb
升级"成功"不等于"健康"：rollout status 只看 Pod 是否 Ready，真正决定业务是否受影响的是 readinessProbe 和 minReadySeconds。没配好探针，滚动升级会一路绿灯地把坏版本推满。
升级卡住：kubectl rollout status 超时退出后，用 kubectl describe deploy/my-app 看 Conditions，常见原因是新 Pod 起不来（镜像拉取失败、资源不足、探针不过）。spec.progressDeadlineSeconds（默认 600s）到点会标记 ProgressDeadlineExceeded

查看历史版本：kubectl rollout history deployment/my-app

回退版本：kubectl rollout undo deployment/my-app --to-revision=num

手动扩缩容：kubectl scale deployment/my-app --replicas=5

# 创建 HPA 自动扩缩容（CPU 70%，2~10 个副本）

kubectl autoscale deployment/my-app --min=2 --max=10 --cpu-percent=70
```

### 3.迁移的思路

简单来说就是将docker compose中的东西全部写成k8s中的资源对象文件

###### 1.docker compose中的容器服务>>>转换成k8s中的Deployment，决定镜像，副本数，探针(在pod模板里的容器上)，以下为deployment的示例

```
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-app
spec:
  replicas: 3
  template:
    spec:
      containers:

   - name: app
     image: registry/app:v2
     ports:
     - containerPort: 8080

    startupProbe:                  # 给慢启动留 5 分钟窗口
      httpGet:
        path: /healthz
        port: 8080
      periodSeconds: 5
      failureThreshold: 60         # 60 × 5s = 300s 内起来就算成功

    readinessProbe:
      httpGet:
        path: /ready
        port: 8080
      periodSeconds: 5
      timeoutSeconds: 2
      failureThreshold: 3          # 连续 3 次失败才摘流量

    livenessProbe:
      httpGet:
        path: /healthz
        port: 8080
      periodSeconds: 10
      timeoutSeconds: 2
      failureThreshold: 3
      initialDelaySeconds: 0       # 有 startupProbe 时通常不用设
```

###### 2.environment环境变量>>>转换成k8s中的configmap与secret，让配置文件外置（有两种方法导入pod）,以及密码安全。

如果不用secret的话，密码有三种方式

1.在deployment中用env直接明文写出

```
containers:
- name: app
  image: my-app:v1
  env:
  - name: DB_PASSWORD
    value: "p@ssw0rd123"     # 直接写在 yaml 里
```

2.用configmap----换个地方本质还是明文

```
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
data:
  DB_PASSWORD: "p@ssw0rd123"   # 明文，不做任何编码
---
envFrom:
- configMapRef:
    name: app-config
#上面是环境变量注入pod
```

3.直接写入镜像Dockerfile ENV DB_PASSWORD=xxx，非常不安全，docker history都能找出且改密码要重新构建镜像

###### 3.volume数据卷>>转换成k8s中的pvc进行数据持久化。这里也分为静态供给与动态供给

###### 4.端口映射>>转化成k8s对应的service+ingress，实现服务发现与统一入口。(具体实现原理参考前面的service笔记)

总而言之，一个服务对应到k8s中就是

```
Deployment（怎么跑） 

+Service（怎么找它）

+PVC（数据放哪，有状态才要）

+ConfigMap/Secret（配置放哪）

+一条 Ingress 规则（外部怎么进）
```

后端 Pod 执行业务逻辑，期间通过**集群 DNS** 连各种中间件——`mysql-svc:3306`、`redis-svc:6379`、`minio-svc:9000`、`milvus-svc:19530`、`etcd-svc:2379`，全是 ClusterIP 东西向流量，一跳 NAT 直达目标 Pod，**完全不出集群、不经过 ingress-nginx**

### 4.完整梳理顺序

```properties
1.盘点项目服务有几个：前端/后端/MySQL/Redis/Milvus/……

- 每个服务：什么镜像、什么端口、依赖谁、数据要不要留

2.准备镜像，统一推进harbor仓库

- 有 Dockerfile 的服务：构建（后端 Maven 打 jar → 打镜像；前端 npm 构建 → nginx 镜像）
- 中间件基础镜像（mysql/redis/nginx/etcd/minio/milvus）：从公网拉到 Harbor
- 为什么统一放 Harbor：**内网可拉、离线可部署、版本可控**

3.写布置清单

先创建一个项目命名空间，再创建secret/configmap资源文件，然后部署中间件(MySQL/Redis/Milvus)，再是后端，前端，最后统一入口ingress

先中间件后应用：**应用启动时就要连中间件**（真实踩坑：Milvus 没就绪，后端 10 秒超时直接崩溃）。

4.部署验证

kubectl get pods → 看日志 → curl 接口 → 浏览器登录。
```



### 5.可能遇到的坑

1. **Milvus 启动时强连接**：客户端初始化就直连（约 10 秒超时），Milvus 没就绪后端直接崩溃 → 所以必须先部署中间件再起应用，这也解释了为什么 K8s 没有 depends_on 要靠部署顺序+探针。
2. **etcd 镜像没有 ENTRYPOINT**：只写 args 会被当成可执行文件 → YAML 里必须 command: ["etcd"] + args。要点：镜像的 Entrypoint/Cmd 决定你 YAML 里写 command 还是 args。**Entrypoint ↔ command，Cmd ↔ args**。
3. **npm install 卡死**：npm 10 装完依赖后的 audit 请求会长时间挂起 → 构建命令加 --no-audit --no-fund。要点：构建阶段的坑和可重复性。
4. **前端大小写问题**：Windows 开发不敏感，Linux 构建报"Could not resolve" → 3 处 import 大小写与文件名不一致，已修正。要点：环境差异。
5. **对外访问端口**：ingress-nginx 是 80:32299，节点 80 端口没监听 → 访问必须带端口 http://192.168.88.102:32299/。要点：Service 的 port 与 nodePort 的区别。

  replicas: 1
