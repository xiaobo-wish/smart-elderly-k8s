# xhzb-mysql 部署排障记录

> 环境：K8s 集群 3 节点（master01 / node01 / node02），命名空间 `xhzb`，MySQL 8.0，镜像来自 `harbor:443/xhzb/mysql:8.0`，存储为 NFS（服务端 192.168.88.100）。

---

## 一、问题总览

本次实际踩了三个坑，是一条**链式因果**：前面的没解决就看不到后面的。

| # | 阶段 | 现象 | 根因 | 状态 |
|---|------|------|------|------|
| 1 | Pending | `pod has unbound immediate PersistentVolumeClaims` | PVC 拿不到卷，集群缺 `nfs-storage` 供给者 | 已解决 |
| 2 | PVC Pending | `xhzb-mysql-pvc` 一直 Pending | 无 StorageClass / 无 provisioner | 已解决 |
| 3 | ContainerCreating | `mount.nfs: access denied by server` | NFS 服务器未建目录 + 未加入 `/etc/exports` | 已解决 |

## 二、问题一：Pod 一直 Pending（PVC 未绑定）

### 现象

```
Events:
  Warning  FailedScheduling  0/3 nodes are available:
           pod has unbound immediate PersistentVolumeClaims. not found
```

### 关键认知

**Pending ≠ 调度不上节点。** 这次的报错虽然挂在 `FailedScheduling` 下面，但内容是「Pod 还有未绑定的 PVC」。原因：PVC 使用 `volumeBindingMode: Immediate`，调度器必须等卷绑好才肯把 Pod 落到节点上。

判断口诀：

- 报错里带 **PersistentVolumeClaim** → 查存储
- 报错里带 **Insufficient cpu/memory** 或 **untolerated taint** → 查节点资源/污点
- 报错里带 **exceeded quota** → 查 ResourceQuota

### 触发原因

Deployment 里 PVC 指定了 `storageClassName: nfs-storage`，但集群里**没有对应的 provisioner 在运行**，PVC 没有人给它建 PV。

### 解决方案

两种，按场景选：

**方案 A：静态 PV（本次采用，最快验证）**

```yaml
apiVersion: v1
kind: PersistentVolume
metadata:
  name: xhzb-mysql-pv
spec:
  capacity:
    storage: 10Gi
  accessModes:
    - ReadWriteOnce
  persistentVolumeReclaimPolicy: Retain
  storageClassName: nfs-storage
  nfs:
    server: 192.168.88.100
    path: /data/nfs/xhzb-mysql
```

**方案 B：动态供给（长期方案，一劳永逸）**

部署 `nfs-subdir-external-provisioner`（ServiceAccount + ClusterRole/Binding + Role/Binding + Deployment + StorageClass），以后新建 PVC 会自动出卷，不用再手工建 PV。

### 验证

```bash
kubectl get pvc -n xhzb     # STATUS: Pending → Bound
kubectl get pod -n xhzb -w  # Pending → ContainerCreating
```

## 三、问题二：Pod 卡在 ContainerCreating（NFS 挂载被拒）

### 现象

```
Events:
  Warning  FailedMount  MountVolume.SetUp failed for volume "xhzb-mysql-pv" :
           mount failed: exit status 32
           Mounting arguments: -t nfs 192.168.88.100:/data/nfs/xhzb-mysql ...
           Output: mount.nfs: access denied by server while mounting 192.168.88.100:/data/nfs/xhzb-mysql
```

### 根因（两条同时存在）

1. NFS 服务器上 `/data/nfs/xhzb-mysql` **目录不存在**；
2. `/etc/exports` 里**只导出了 `/var/webroot`**，新目录没登记，客户端无权挂载。

### 解决步骤（在 NFS 服务器 192.168.88.100 上）

```bash
# 1. 建目录
mkdir -p /data/nfs/xhzb-mysql

# 2. 放开写权限（容器内 mysql 用户 uid=999）
chmod 777 /data/nfs/xhzb-mysql        # 或：chown 999:999 /data/nfs/xhzb-mysql

# 3. 登记到导出表
echo '/data/nfs/xhzb-mysql 192.168.88.0/24(rw,sync,no_subtree_check,no_root_squash)' >> /etc/exports

# 4. 重新发布（改文件不生效，必须执行这一步）
exportfs -arv
exportfs -v                            # 核对已生效的导出列表
```

参数说明：

- `no_root_squash`：不加的话 root 会被压成 `nfsnobody`，MySQL 初始化写不进去
- `no_subtree_check`：避免子目录校验导致挂载被拒
- `192.168.88.0/24`：允许挂载的客户端网段，按实际网络改

### 节点侧验证（node02 上执行）

```bash
showmount -e 192.168.88.100                 # 能看到该路径才算修好
mkdir -p /mnt/t
mount -t nfs 192.168.88.100:/data/nfs/xhzb-mysql /mnt/t && ls -ld /mnt/t
umount /mnt/t
```

### 重要

**不需要删 Pod。** kubelet 每约 30 秒自动重试一次挂载，修好服务端后下一次重试就成功。想立刻生效才手动删除：

```bash
kubectl delete pod -n xhzb -l app=xhzb-mysql
```

## 四、NFS 导出机制要点（这次的核心知识点）

1. **服务端只发布 `/etc/exports` 里显式列出的路径**，客户端只能挂这些路径。新建目录不会自动被共享。
2. **子目录不跨路径继承**：导出 `/data/nfs` 时其子目录通常可挂；但只导出 `/var/webroot` 时，`/data/nfs/xhzb-mysql` 是另一条路，必须单独登记。
3. **改完 `/etc/exports` 必须 `exportfs -arv`** 才生效，`exportfs -v` 用来核对。
4. **权限要落到文件系统上**：光有导出选项不够，目录本身要允许 uid 999 写入。

## 五、排查命令速查表

```bash
# 第一现场：Events 是唯一真相
kubectl describe pod -n xhzb -l app=xhzb-mysql | sed -n '/Events:/,$p'
kubectl get events -n xhzb --sort-by=.lastTimestamp | tail -30

# 存储
kubectl get sc                        # 有哪些 StorageClass
kubectl get pvc -n xhzb               # PVC 是否 Bound
kubectl describe pvc xhzb-mysql-pvc -n xhzb
kubectl get pv                        # 静态 PV 是否创建

# 配置与网络
kubectl get cm -n xhzb                # ConfigMap xhzb-sql 是否存在
kubectl get pod -n kube-system -o wide | grep -Ei 'calico|flannel|cilium'

# 日志
kubectl logs -n xhzb deploy/xhzb-mysql --tail=50
```

### ContainerCreating 常见原因对照

| Events 关键词 | 含义 | 处理 |
|---|---|---|
| `FailedMount` / `mount failed` | 卷挂载失败（NFS 最常见） | 修 `/etc/exports`、装 `nfs-utils`、查 `showmount -e` |
| `FailedCreatePodSandBox` / `cni` | CNI 网络插件未就绪 | 查 kube-system 下的 calico/flannel |
| `Failed to pull image` / `no such host` / `x509` | 镜像仓库不可达或证书问题 | 节点 hosts 解析 harbor、配置 insecure registry、`imagePullSecrets` |
| `configmap "xxx" not found` | ConfigMap 缺失 | `kubectl create cm` |
| 无报错、纯等待 | 卷挂载慢 / MySQL 初始化慢 | 耐心等，NFS 上初始化可能要数分钟 |

## 六、后续注意事项

1. **确认初始化完成**
   ```bash
   kubectl logs -n xhzb deploy/xhzb-mysql | tail -20   # 看到 ready for connections
   ```

2. **确认 init SQL 生效**（`/docker-entrypoint-initdb.d` 下的脚本只在数据目录为空时执行一次）
   ```bash
   kubectl exec -n xhzb deploy/xhzb-mysql -- mysql -uroot -p"$MYSQL_ROOT_PASSWORD" -e "show tables from xhzb;"
   ```

3. **`lost+found` 隐患**：若数据目录挂载点下存在 `lost+found`，MySQL 会因数据目录非空导致初始化失败。建议加 `subPath`：
   ```yaml
   volumeMounts:
     - name: data
       mountPath: /var/lib/mysql
       subPath: mysql
   ```

4. **生产化补全**（当前 YAML 还缺这些）
   - `resources.requests/limits`：现在是 `BestEffort`（QoS 最低），节点压力大时最先被驱逐
   - `livenessProbe` / `readinessProbe`：建议用 `mysqladmin ping` 或 TCP 3306 探活
   - `imagePullSecrets`：harbor 若是私有仓库必须配置
   - **存储介质**：MySQL 跑在 NFS 上 IO 延迟高、锁机制不可靠，生产建议 local PV 或云厂商块存储，NFS 仅适合测试/开发环境

5. **MySQL 8 认证插件**：默认 `caching_sha2_password`，老版本客户端连不上，必要时加启动参数
   ```yaml
   args:
     - --default-authentication-plugin=mysql_native_password
   ```
