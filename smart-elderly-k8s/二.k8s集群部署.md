# 二.k8s集群部署

[TOC]

##### 1.k8s是什么？

```properties
kubernetes是容器集群管理系统，可以实现容器集群的自动化部署，自动扩缩容，自动维护等，让容器化应用更加稳定，高效，自动的运行。
```

##### 2.k8s有什么功能？

```properties
容器调度：自动将容器部署到最适合的节点上

自动伸缩：根据负载自动扩容/缩容容器实例

服务发现与负载均衡：内置服务发现和请求分发机制

自愈能力：容器挂了，会自动重启或替换

滚动更新与回滚：支持平滑升级与快速回滚

配置与密钥管理：通过configmap与secret管理应用配置

存储管理：支持持久化存储（PV/PVC），挂载到pod,容器重启迁移数据不丢失
```

##### 3.传统部署与k8s部署的对比

```properties
环境一致性：通过容器镜像封装应用及全部依赖，开发、测试、生产环境完全一致，真正实现"一次构建，到处运行"

弹性伸缩：支持 HPA 自动扩缩容，根据 CPU/内存/自定义指标自动增减 Pod 副本，秒级响应流量波动

资源利用率高：多应用共享节点资源，通过 requests/limits 精细控制配额，资源利用率从传统的 15%-20% 提升至 60%-80%

部署升级简单：声明式 YAML 配置，kubectl apply 一键部署；滚动更新零停机，失败可一键回滚

运维自动化：内置自愈能力（Pod 崩溃自动重建）、服务发现、负载均衡，大幅降低人工运维成本

```

##### 4.kubernetes集群架构

核心架构：master管理节点，node计算节点， image镜像仓库

![image-20260920195140987](二.k8s集群部署.assets/image-20260920195140987.png)

```properties
1.控制平面组件
	API Server ：集群的唯一入口，所有的操作都要通过它（kubectl等）

​	etcd ：分布式键值存储，用于保存集群的所有配置和状态数据，相当于k8s的数据库

​	Control Manager：运行各种控制器，用于确保集群状态与期望状态一致

​	Scheduler：调度器，负责把pod分配到合适的节点上，要考虑各种规则以及打分
```

```properties
2.node节点组件

​	kubelet：节点的代理，负责与API Server 通信，保证本节点的pod按照预期运行

​		监听API Server--watch 分配到当前节点的pod清单

​		管理pod生命周期，调用CRI接口（containerd）拉镜像，创建pod沙箱，启停容器

pod沙箱-->>沙箱就是 pause 容器，是 Pod 里第一个启动的容器，代表 Pod 的网络、命名空间底座。后续再启动pod里面的业务容器加入到pause的命名空间，所有业务容器共享一个pod ip

​		节点状态上报给API server

​	     内置cAdvisor：采集节点信息，提供给metrics-server

​		节点证书管理：kubelet开启serverTLSBootstrap: true配置后，会自动生成CSR，向集群API Server 申请kubelet服务端证书（这是提供给metrics-server的，所以它是服务端，指标聚合器（pod状态）是客户端来通过kubelet获取节点信息），然后master管理节点批准该CSR（用CA私钥签名），生成的证书用于10250端口，metrics-server通过https访问节点的kubelet10250端口，就可以拿到节点信息了。（用集群CA公钥校验证书）metrics-server 容器内内置集群 CA 根证书，用来验证 kubelet 证书。

​	kube-proxy：负责node的网络代理，实现Service的负载均衡和网络转发

​	容器运行时：实际运行容器的软件containerd，k8s通过CRI与他交互（containerd runtime interface），容器运行时是实际负责管理容器生命周期的软件。Kubelet 通过 CRI 容器运行时接口与容器运行时通信
```

```properties
3.附加组件，增强集群功能

DNS：为pod和service提供域名解析

Dashboard：k8s集群的可视化界面

metrics server ：资源指标采集

ingress controller：提供http/https访问入口

CNI插件：必须组件，为pod分配IP地址实现集群网络通信

calico：提供网络和网络策略

```

7.master初始化

```shell
#模拟初始化

cd kubernetes

kubeadm init --config=init/init.yaml --dry-run 2>err.log

cat error.log

rm -rf error.log /etc/kubernetes/tmp

#拷贝证书文件

scp harbor:/usr/local/harbor/tls/cert.crt /etc/pki/ca-trust/source/anchors/harbor-ca.crt

update-ca-trust

ls -l /etc/pki/ca-trust/source/anchors/harbor-ca.crt

#这条 scp 命令从 harbor 服务器远程拷贝 harbor 的 CA 根证书（自签名，用自己的私钥签自己的公钥），放到 CentOS 系统的信任锚目录；执行 update-ca-trust extract 更新系统证书库后，本节点所有程序都会信任该自建 CA，访问 Harbor HTTPS 不会报证书未知机构错误。也就是说里面有CA公钥，访问harbor服务端时，他给你发送服务端的证书，使用公钥去验证私钥从而确定服务是否正确。

-  CA 根证书 ca.crt：给别人做校验用，分发到所有节点；里面是CA 公钥
-  CA 私钥 ca.key：用来签发证书、做签名；绝对不能分发，保存在 CA 服务器
-  服务端证书 server.crt：CA 签发出来给 Harbor 服务使用，里面存放 Harbor 服务的公钥

把 `server.crt` + `server.key` 放到 Harbor (Nginx) 配置，用于 HTTPS 服务。 

CA 的 ca.crt 分发到所有客户端节点（k8s 节点），用于校验 server.crt 的签名。

#给 Containerd 创建 Harbor 证书目录

mkdir -p /etc/containerd/certs.d/harbor:443

#把 CA 放到证书目录

cp /etc/pki/ca-trust/source/anchors/harbor-ca.crt /etc/containerd/certs.d/harbor:443/ca.crt

 vim /etc/containerd/certs.d/harbor:443/hosts.toml

server = "https://harbor:443" 

[host."https://harbor:443"]  

​	capabilities = ["pull", "resolve", "push"]  

​	ca = "/etc/containerd/certs.d/harbor:443/ca.crt"

#修改第31行的内容

vim /etc/containerd/config.toml 31       

config_path = '/etc/containerd/certs.d'

 #验证配置文件 

[root@master01 ~]# containerd config dump >/dev/null 

[root@master01 ~]# echo $? 

[root@master01 ~]# systemctl restart containerd

#初始化master节点

cd kubernetes

kubeadm init --config=init/init.yaml | tee init/init.log

 mkdir -p $HOME/.kube

sudo cp -i /etc/kubernetes/admin.conf $HOME/.kube/config

sudo chown $(id -u):$(id -g) $HOME/.kube/config

kubectl get nodes
```
